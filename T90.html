T90 Report

A reconstruction of an Excel and Power Query tool used to monitor projects scheduled to launch within the next 90 days and identify those that may be at risk due to missing or delayed inputs across functional partners.

Back to Projects

Description

This project reconstructed the T90 (T-minus 90 Days) Report generation process used to monitor projects forecasted to launch within the next 90 days. The purpose of the T90 workflow is to identify projects that may be at risk of delayed activation due to missing or late inputs across operational partners (Legal, Field Operations, Billing, Internet Connectivity, Video Connectivity, and Voice Connectivity) required for launch. The redesign focused on stabilizing and simplifying a multi-workbook Excel and Power Query process that captures a data snapshot on Fridays and compares to refreshed current-state data the following week.

Key enhancements included consolidating and standardizing query logic, optimizing query performance, simplifying dependency calculations, adding logic to identify resolved and forecast-shifted records, and introducing a unique status field with a custom connection between the T90 dashboard and the source SharePoint List, enabling updates made in the Excel table to flow back to the underlying source data. The solution also introduced a method for preserving manual user-entered closure decisions through refreshes by using Excel helper tables and Power Query merge-back logic, allowing the workbook to behave more like an interactive dashboard while retaining end-user inputs. Additional improvements included dynamic retrieval of Friday snapshot dates from the source workbook, summary metrics for total projects within the date range and those at risk, and synchronized redesigns for two parallel reporting paths serving different project populations.

Together, these changes created a more consistent, accurate, and maintainable launch-readiness reporting framework. The finished product eliminated the need for an additional helper workbook and replaced a fragile, manual copy-and-paste workflow with a streamlined and sustainable reporting solution.

The T90 report generation workflow begins with a Friday snapshot of projects forecasted to launch within the next 90 days. That snapshot is used to identify projects at risk based on missing or delayed readiness inputs. The report is then refreshed on Tuesday and Thursday to monitor whether those at-risk projects are progressing toward launch readiness, while preserving user-entered closure decisions and updated status handling.

Legacy Workflow Overview

The legacy T90 process relied on a multi-workbook handoff chain that moved data from an Extract workbook into an Intermediate Template workbook and then into the Final reporting workbook. While functional, that structure created duplicated logic, repeated refresh activity, and several manual transfer points that increased maintenance effort and process fragility.

The legacy workflow depended on sequential workbook handoffs. Data was first prepared in the Extract workbook, manually passed into an Intermediate Template workbook for refreshed comparison and shaping, and then copied again into the Final report workbook for dashboard assembly and user review.

Legacy T90 Workflow

The inherited reporting process was divided across multiple workbooks, each responsible for a separate stage in the reporting chain. Legacy Extract Workbook: Baseline Snapshot Layer

In the legacy process, the Extract workbook used a three-query pipeline to generate the baseline Friday snapshot that anchored the rest of the weekly T90 workflow. It pulled source data from SharePoint, isolated the full 90-day project population, and narrowed that set to the projects considered at risk for dashboard reporting.

How the legacy Extract Workbook functioned:

  1. Pull raw data from the SharePoint source list
  2. Clean and reshape the source data into a master readiness dataset
  3. Calculate a high-level readiness/date-risk flag for each project
  4. Filter the master dataset to projects within the current T90 window
  5. Further filter that in-range population to the projects considered at risk
  6. Output the resulting extract as the Friday baseline snapshot for downstream use

Legacy T90 Report Workbook: Manual Report Assembly and Refresh Layer

In the legacy process, the T90 Report workbook was updated through a largely manual weekly routine that depended on copy/paste transfers from the intermediate workbook, repeated worksheet duplication, manual filtering and cleanup, hand-applied formatting, and manual entry of summary dates and counts. What is now handled automatically through Power Query, pull-through tables, and conditional formatting previously required a time-consuming sequence of repetitive user actions each reporting cycle.

How the legacy T90 Report functioned:

  1. Refresh the intermediate workbook and manually remove records whose updated forecast dates had moved outside the active T90 range
  2. Duplicate the previous report tabs in the T90 Report workbook to create new weekly report tabs for each reporting path
  3. Update the worksheet names to reflect the current extract date and refresh date
  4. Manually transfer the refreshed data into the new report tabs from the intermediate workbook
  5. Manually clean, filter, and sort the report output, including removing closed records and ordering by forecast date
  6. Manually apply cell formatting and enter summary counts and date values that are now generated automatically in the redesigned solution

New Extract Workbook: Dynamic Snapshot and Metrics Layer

In the redesigned process, the Extract workbook was rebuilt as a cleaner and more modular snapshot layer that automatically defines the current T90 reporting window, isolates in-scope and at-risk projects, and produces reusable summary metrics for the Final dashboard. Compared with the legacy version, it requires less maintenance, uses dynamic date logic, and supports downstream reporting more directly.

How the new Extract workflow functions:

  1. Pull and standardize current Launch Readiness data from SharePoint
  2. Calculate the core readiness/date-risk status in a simplified base query
  3. Dynamically define the reporting window using current-date parameter queries
  4. Filter to projects forecasted within the next 90 days and not yet activated
  5. Isolate the subset of in-range projects with readiness issues or missing required dates
  6. Generate reusable counts and reporting-window dates for direct pull-through into the Final dashboard

Key Improvements in the Redesigned Process

The redesigned T90 solution improved both the technical structure of the reporting process and the end-user experience of maintaining the dashboard week over week.

  1. Removed the intermediate workbook dependency. The Friday snapshot now flows directly from the Extract workbook into the Final workbook, eliminating a separate staging file and a manual handoff step.
  2. Consolidated reporting logic. Comparison logic, display formatting, closure handling, and user-facing dashboard preparation were brought together into a more centralized Final workbook design.
  3. Improved query focus and maintainability. Source-loading and transformation logic were streamlined so queries pulled the fields actually needed for reporting and reduced unnecessary complexity.
  4. Added reusable support outputs. Extract dates and counts were exposed as query-driven outputs and pulled directly into the dashboard, reducing manual maintenance.
  5. Preserved user-entered closure decisions across refreshes. Helper queries and merge-back logic created a durable pattern for retaining manual status handling during automated refresh cycles.
  6. Enabled source-system synchronization. A custom write-back field created a more interactive connection between the dashboard and the underlying SharePoint source data.

Outcome

The finished redesign created a more consistent, accurate, and sustainable launch-readiness reporting framework. It reduced file sprawl, shortened the reporting path, improved visibility into project status, and made the Final workbook behave more like an interactive dashboard rather than a static downstream report.

By consolidating logic, reducing manual maintenance, and preserving user inputs through refreshes, the new structure turned a fragile multi-workbook process into a more reliable and maintainable reporting solution.
